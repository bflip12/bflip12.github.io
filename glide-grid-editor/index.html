Why Glide Data Grid

The app let users create custom fields: extra columns of values for each record. Changing a value meant downloading an Excel template, editing it offline, and uploading it again. The task was to let users edit the values in place.

I first tried the grid library the app already used for its tables. It renders cells as DOM elements, and at this size it was too slow. That led me to Glide Data Grid, which draws cells on a canvas instead. The default view held about 25,000 cells.

Glide handles drawing, selection, keyboard movement, copy, and a cell editor. Everything about what changed is yours to build:

Step 1

Key everything by row ID

Glide identifies a cell by its position: column index and row index on screen. Storing edits the same way works until the rows move. A filter, a sort, or a new row changes which row sits at each position, and an edit stored as "row 2" now points at a different row.

Store values and edits by row ID instead, and keep the order on screen as a separate, derived list, visibleRowIds. Row N on screen is visibleRowIds[N]. Column 0 is the read-only ID column, and data column i is grid column i + 1. 

type ColumnT = {
  id: string;
  title: string;
  values: Record<string, string>; // row ID -> value
  isNew?: boolean; // added in the editor, not saved yet
};

type GridEditorStateT = {
  idColumnTitle: string;
  rowIds: string[]; // every row, in order
  columns: ColumnT[]; // current values
  savedColumns: ColumnT[]; // values as last saved
  changes: Map<string, Map<string, string>>; // column ID -> row ID -> new value
  filters: Record<string, "all" | "hasValue" | "noValue">;
};
Full code: getCellContent 
const getCellContent = ([col, row]: Item): GridCell => {
  const rowId = visibleRowIds[row] ?? "";

  if (col === 0) {
    return {
      kind: GridCellKind.Text,
      data: rowId,
      displayData: rowId,
      allowOverlay: false,
      readonly: true
    };
  }

  const column = columns[col - 1];
  const value = column?.values[rowId] ?? "";
  const isChanged = column ? changes.get(column.id)?.has(rowId) === true : false;

  return {
    kind: GridCellKind.Text,
    data: value,
    displayData: value,
    allowOverlay: true,
    // Canvas cannot read CSS variables, so this is a real colour value.
    themeOverride: isChanged ? { bgCell: colors.changedCellBg } : undefined
  };
};

Step 2

Keep the state in a reducer and share it with context

The grid, the toolbar, the change count, and the save button all read the same state. A reducer keeps every change a pure function you can test without rendering a canvas, and one context provider shares it. 

type GridEditorActionT =
  | { type: "load"; data: GridDataT }
  | { type: "applyChanges"; changes: CellChangeT[] }
  | { type: "addColumn"; title: string }
  | { type: "removeColumn"; columnId: string }
  | { type: "setFilter"; columnId: string; filter: ColumnFilterT }
  | { type: "saved"; request: SaveRequestT };

The provider derives the visible rows, the change count, and the save request instead of storing them, so they can never disagree with the data. Every component that reads the context re-renders on each change. With four components and a grid that redraws on a canvas anyway, that costs little. The version I shipped used Jotai atoms with the same split: base atoms for the data and edits, derived atoms for everything else.

Full code: the provider 
export const GridEditorProvider = ({ initialData, children }: GridEditorProviderPropsT) => {
  const [state, dispatch] = useReducer(gridEditorReducer, initialData, createGridEditorState);

  const visibleRowIds = useMemo(
    () => getVisibleRowIds(state.rowIds, state.columns, state.filters),
    [state.rowIds, state.columns, state.filters]
  );

  const value = useMemo(() => {
    const changeCount = countChanges(state.changes);
    return {
      state,
      dispatch,
      visibleRowIds,
      changeCount,
      hasChanges: changeCount > 0 || state.columns.some((column) => column.isNew),
      saveRequest: buildSaveRequest(state.columns, state.changes)
    };
  }, [state, visibleRowIds]);

  return <GridEditorContext.Provider value={value}>{children}</GridEditorContext.Provider>;
};

Step 3

Record edits in a change map

The change map goes column ID, then row ID, then new value. Each changed cell has one entry however often it is edited, and checking whether a cell changed is two Map reads, which matters because getCellContent runs for every visible cell when the grid draws. An edit that puts a cell back to its saved value removes the entry, so the counter never reports a cell that matches the server.

Glide reports typed edits through onCellsEdited as locations and new cells. Convert each location to a column ID and row ID, dispatch once, and return true so Glide does not also call onCellEdited for each cell. 

const onCellsEdited = (edits: readonly EditListItem[]) => {
  const cellChanges: CellChangeT[] = [];

  for (const { location, value } of edits) {
    const [col, row] = location;
    const column = columns[col - 1];
    const rowId = visibleRowIds[row];
    if (col === 0 || !column || rowId === undefined) continue;
    if (value.kind !== GridCellKind.Text) continue;
    cellChanges.push({ columnId: column.id, rowId, value: value.data });
  }

  dispatch({ type: "applyChanges", changes: cellChanges });
  return true;
};
Full code: addChangesToMap and the reducer case 
export const addChangesToMap = (
  current: ChangeMapT,
  changes: CellChangeT[],
  savedColumns: ColumnT[]
): ChangeMapT => {
  const next = new Map(current);
  const copied = new Set<string>();
  const savedById = new Map(savedColumns.map((column) => [column.id, column.values]));

  for (const { columnId, rowId, value } of changes) {
    // Copy each inner map once per call, not once per cell.
    if (!copied.has(columnId)) {
      next.set(columnId, new Map(next.get(columnId)));
      copied.add(columnId);
    }
    const columnChanges = next.get(columnId)!;
    const savedValue = savedById.get(columnId)?.[rowId] ?? "";

    if (value === savedValue) columnChanges.delete(rowId);
    else columnChanges.set(rowId, value);
  }

  // Drop columns left with no changes.
  copied.forEach((columnId) => {
    if (next.get(columnId)?.size === 0) next.delete(columnId);
  });

  return next;
};
case "applyChanges": {

  const byColumn = new Map<string, Record<string, string>>();
  for (const { columnId, rowId, value } of action.changes) {
    if (!byColumn.has(columnId)) byColumn.set(columnId, {});
    byColumn.get(columnId)![rowId] = value;
  }

  const columns = state.columns.map((column) => {
    const updates = byColumn.get(column.id);
    return updates ? { ...column, values: { ...column.values, ...updates } } : column;
  });

  return {
    ...state,
    columns,
    changes: addChangesToMap(state.changes, action.changes, state.savedColumns)
  };
}

Step 4

Handle paste yourself

Glide's onPaste receives the target cell and the pasted text as rows of strings. Return true and Glide writes the values through onCellsEdited, skipping read-only cells. Return false and the paste is yours. I handle it for two things Glide cannot know: whether the first row is a header, and whether the paste is too large to save. 

const onPaste = (target: Item, values: readonly (readonly string[])[]) => {
  const { changes, isHeaderRowSkipped } = getPasteChanges({
    target,
    values,
    visibleRowIds,
    idColumnTitle,
    columns
  });
  if (changes.length === 0) return false;

  const bytes = estimatePayloadBytes(changes); // UTF-8 length of the JSON
  if (bytes > maxPayloadBytes) {
    onPasteRejected(`This paste is ${formatMegabytes(bytes)}, over the limit.`);
    return false;
  }

  dispatch({ type: "applyChanges", changes });
  if (isHeaderRowSkipped) onHeaderRowSkipped();
  return false; // already applied, so Glide must not apply it again
};

Skip a pasted header row

A whole column copied from a spreadsheet starts with its header cell. Paste it with the grid's column header selected and Glide starts at row 0, so the header lands in the first row as data. Glide's own copy leaves headers out unless copyHeaders is on, so the header row only comes from other sources. isHeaderRow compares the first pasted row with the titles of the columns it lands on, and only runs when the paste starts at the top row and has more than one row.

Map the paste to row IDs

getPasteChanges puts each pasted row on the next visible row, so a paste into a filtered grid writes to the rows the user can see. Values that land on the ID column are dropped without shifting the rest, and anything past the last row or column is dropped. The server in the app accepted requests up to 50 MB, so the paste is measured before anything changes.

Full code: getPasteChanges and isHeaderRow 
export const getPasteChanges = ({
  target,
  values,
  visibleRowIds,
  idColumnTitle,
  columns
}: GetPasteChangesParamsT): GetPasteChangesReturnT => {
  const [targetCol, targetRow] = target;
  const gridTitles = [idColumnTitle, ...columns.map((column) => column.title)];

  const isHeaderRowSkipped =
    targetRow === 0 && values.length > 1 && isHeaderRow(values[0], gridTitles, targetCol);
  const firstDataRow = isHeaderRowSkipped ? 1 : 0;

  const changes: CellChangeT[] = [];

  for (let pasteRow = firstDataRow; pasteRow < values.length; pasteRow++) {
    const rowId = visibleRowIds[targetRow + pasteRow - firstDataRow];
    if (rowId === undefined) break;

    values[pasteRow].forEach((value, offset) => {
      const gridCol = targetCol + offset;
      if (gridCol === 0) return; // read-only ID column

      const column = columns[gridCol - 1];
      if (!column) return;

      changes.push({ columnId: column.id, rowId, value });
    });
  }

  return { changes, isHeaderRowSkipped };
};
const normalize = (text: string) => text.trim().toLowerCase();

export const isHeaderRow = (
  row: readonly string[],
  gridTitles: string[],
  startColumn: number
): boolean => {
  let matched = 0;

  for (let offset = 0; offset < row.length; offset++) {
    const cell = normalize(row[offset] ?? "");
    if (cell === "") continue;

    const title = gridTitles[startColumn + offset];
    if (title === undefined || normalize(title) !== cell) return false;
    matched += 1;
  }

  return matched > 0;
};

Step 5

Add and remove columns

A new column goes into the state straight away, marked isNew, and is created on the server with the next save. Its title cannot be empty after trimming and cannot match an existing column. The comparison is case-sensitive, as it was in the shipped version. Lowercase both sides if your backend treats "Depth" and "depth" as the same. 

export const validateColumnTitle = (title: string, columns: ColumnT[]): ColumnTitleValidationT => {
  const trimmed = title.trim();

  if (trimmed === "") return { isValid: false, error: "Column name is required" };
  if (columns.some((column) => column.title === trimmed)) {
    return { isValid: false, error: `Column "${trimmed}" already exists` };
  }

  return { isValid: true };
};

Only unsaved columns can be removed. Removing one also removes its pending edits and its filter, so the next save never sends cells for a column that no longer exists.

Step 6

Filter rows without losing edits

Each column's header menu offers three filters: all rows, rows with a value, and rows without one. The visible rows are derived from the filters and the current values. Edits never refer to positions, so filtering cannot move them. 

const hasValue = (value: string | undefined) => value !== undefined && value !== "";

export const getVisibleRowIds = (
  rowIds: RowIdT[],
  columns: ColumnT[],
  filters: Record<string, ColumnFilterT>
): RowIdT[] => {
  const active = columns.filter((column) => (filters[column.id] ?? "all") !== "all");
  if (active.length === 0) return rowIds; // same array, so memoised readers do not redraw

  return rowIds.filter((rowId) =>
    active.every((column) =>
      filters[column.id] === "hasValue"
        ? hasValue(column.values[rowId])
        : !hasValue(column.values[rowId])
    )
  );
};

Because the filter reads current values, filling in a cell under "rows without a value" removes that row from view as soon as the edit is applied. The edit stays recorded against its row ID, and the row returns when the filter is cleared.

Step 7

Save in one request

The request lists the columns to create and every changed cell. Cells in new columns are ordinary entries in the change map, so each cell appears once. The request is size-checked again before it is sent, since many small edits add up, and pending changes are cleared only after the server accepts them. 

const save = async () => {
  const bytes = estimatePayloadBytes(saveRequest);
  if (bytes > maxPayloadBytes) {
    setError(`These changes are ${formatMegabytes(bytes)}. Save in smaller batches.`);
    return false;
  }

  try {
    await onSave(saveRequest);
    dispatch({ type: "saved", request: saveRequest });
    return true;
  } catch (err) {
    setError(err instanceof Error ? err.message : "Failed to save changes");
    return false;
  }
};
Full code: buildSaveRequest 
export const buildSaveRequest = (columns: ColumnT[], changes: ChangeMapT): SaveRequestT => {
  const newColumns = columns
    .filter((column) => column.isNew)
    .map(({ id, title }) => ({ id, title }));

  const updates: SaveRequestT["updates"] = [];
  changes.forEach((rows, columnId) => {
    rows.forEach((value, rowId) => updates.push({ columnId, rowId, value }));
  });

  return { newColumns, updates };
};

What changed from the version I shipped

The demo and the code repository follow the shipped design, with two differences. The state lives in a reducer and context instead of Jotai atoms, and changed cells are highlighted, where the shipped version highlighted new columns only.

Each reducer case and pure function has its own tests, which is what keeping the logic out of the components is for. The shipped editor had about 150 unit tests. The reference repository has 68, and the demo was checked in a real browser for typing, pasting, filtering, search, and the Escape order.

Summary

Key every edit by row ID. Row positions change whenever the view changes. Row IDs do not.
  • Store values and edits by row ID; derive the visible row order.
  • Keep one change map entry per cell, and drop edits that match the saved value.
  • Handle paste yourself to skip header rows and check the size first.
  • Remove a column's pending edits when the column is removed.
  • Save everything in one request, and clear only what the server accepted.

Handle the keyboard inside a modal

The editor opened in a modal. Two keys needed care there.

Ctrl+F (Cmd+F on macOS) opens the browser's find bar, which cannot search text drawn on a canvas. Glide has its own search bar, controlled by the showSearch prop. Its built-in shortcut is off by default and only works while the grid has focus, so I listen on the document and open the grid's search instead.

Escape can mean several things: close the search, leave the cell editor, clear the selection, or close the modal. One handler decides in that order and does only the first one that applies. It listens in the capture phase on document, so it runs before the grid or the modal sees the key. 

const handleKeyDown = (event: KeyboardEvent) => {
  if ((event.ctrlKey || event.metaKey) && event.key.toLowerCase() === "f") {
    event.preventDefault();
    setIsSearchOpen(true);
    return;
  }
  if (event.key !== "Escape") return;

  const current = latest.current; // refs, so the listener is attached once
  const stop = () => {
    event.preventDefault();
    event.stopPropagation();
  };

  if (current.isSearchOpen) {
    stop();
    setIsSearchOpen(false);
    return;
  }

  // Glide renders the cell editor into #portal. Let the grid close it.
  const portal = document.getElementById("portal");
  if (portal && event.target instanceof Node && portal.contains(event.target)) return;

  if (current.hasSelection) {
    stop();
    current.onClearSelection();
    return;
  }

  if (current.onEscapeWhenIdle) {
    stop();
    current.onEscapeWhenIdle(); // asks to close, with a prompt if there are unsaved changes
  }
};

document.addEventListener("keydown", handleKeyDown, true);

Disable the handler while something above the grid owns the keyboard, such as the "discard changes?" prompt or a column menu. Otherwise Escape on the prompt reaches the grid first.
